# RAG: проверенные источники для презентации

Проверено 13 ноября 2026 года. Статус: исследовательские заметки, не готовые слайды. Использованы первичные источники. Числа разных исследований нельзя объединять в единую шкалу «качества RAG».

## 1. Истоки и проблема RAG

[Lewis et al., Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks, 2020; просмотрена v4 от 2021](https://arxiv.org/html/2005.11401v4).

Исходная работа сочетает генератор BART с поиском по векторному индексу Wikipedia. Мотивация: знания в параметрах модели трудно обновлять, а происхождение ответа трудно проверять. В современном объяснении полезно разделить знания модели и внешние документы, получаемые во время запроса. Доступ к источникам помогает проверке, но сам по себе не гарантирует правильный ответ.

Исторические числа для необязательного графика: Natural Questions, Exact Match, Table 1: T5-11B closed-book 34.5; T5-11B+SSM 36.6; DPR 41.5; RAG-Token 44.1; RAG-Sequence 44.5. Это различные системы из старого исследования, а не эксперимент с добавлением RAG к одной и той же современной LLM. Поэтому для основной презентации предпочтительнее график ниже.

## 2. Улучшения поиска: готовые данные для основного графика

[Anthropic, Introducing Contextual Retrieval, 19 September 2024](https://www.anthropic.com/research/contextual-retrieval).

Показатель: retrieval failure rate = 1 − recall@20; меньше — лучше. Данные усреднены по исследованным доменам (код, художественные тексты, ArXiv, научные статьи), с Gemini Text 004 как выбранной авторами лучшей конфигурацией embeddings.

| Configuration | Retrieval failure rate (%) |
|---|---:|
| Baseline embeddings | 5.7 |
| Contextual embeddings | 3.7 |
| Contextual embeddings + contextual BM25 | 2.9 |
| Contextual embeddings + contextual BM25 + reranking | 1.9 |

Название графика: **Better retrieval reduces missing evidence**. Ось: **Retrieval failure rate (%) — lower is better**. Подпись: **Anthropic, 2024; average across evaluated domains; recall@20-based metric.**

Улучшение 5.7 → 1.9 — это примерно 67% относительного снижения ошибок поиска (авторы округляют), не 67 процентных пунктов и не «точность ответов выросла на 67%». Метод добавляет контекст к фрагментам, сочетает семантический и лексический поиск; reranking отбирает лучшие результаты. Дополнительные этапы также требуют времени и вычислений. Не переносить эти числа на любой RAG.

## 3. GraphRAG: научная основа и ограничения

[Edge et al., From Local to Global: A GraphRAG Approach to Query-Focused Summarization; v2, 19 February 2025, исходный preprint 2024](https://arxiv.org/html/2404.16130v2).

Механизм: сущности и связи → граф → сообщества → предварительные сводки → объединение ответов по сводкам. Задача исследования — глобальные вопросы о коллекции документов, а не только поиск отдельного факта.

Эксперимент: 125 вопросов на каждом из двух корпусов, пять повторений парных LLM-оценок. Корпуса — подкасты (~1 млн токенов), новости (~1.7 млн). Предпочтение по полноте глобальных методов относительно vector RAG составило 72–83% и 72–80% соответственно. Это win rate, а не factual accuracy. Нельзя утверждать универсальное превосходство GraphRAG.

Table 2, необязательные данные: токены контекста Podcast C0 26,657 против TS 1,014,611; News C0 39,770 против TS 1,707,694. TS — map-reduce по всем исходным текстам, НЕ обычный vector RAG. Это не полная стоимость системы: построение индекса не включено. Не подписывать график «GraphRAG на 97% дешевле RAG».

## 4. GraphRAG сегодня — несколько способов поиска

[Microsoft GraphRAG documentation, Query Engine overview](https://microsoft.github.io/graphrag/query/overview/).

Local Search сочетает знания графа и исходные фрагменты для вопросов о конкретных сущностях. Global Search работает со сводками сообществ; документация прямо называет его ресурсоёмким. DRIFT сочетает сведения о сообществах с последующими уточняющими вопросами. Basic Search даёт базовый vector RAG для сравнения. Для 12 слайдов достаточно показать Local/Global словами и одну понятную схему; перечислять все режимы необязательно.

## 5. Проверенная иллюстрация экономики: оптимизация GraphRAG

[Microsoft Research, GraphRAG: Improving global search via dynamic community selection, 15 November 2024](https://www.microsoft.com/en-us/research/blog/graphrag-improving-global-search-via-dynamic-community-selection/).

Сравнение на AP News, 50 глобальных вопросов. Dynamic selection level 1 против static global search level 1: средняя token cost ниже на 77%; по LLM-оценке трёх критериев статистически значимого различия качества не обнаружено. Это не доказательство полного равенства качества. Отсеиваются нерелевантные сводки; небольшой классификатор помогает сократить дорогую генерацию.

Данные для отдельного столбчатого графика **Relative token cost (static search = 100)**:

| Method | Relative token cost |
|---|---:|
| Static GraphRAG global search, level 1 | 100 |
| Dynamic GraphRAG global search, level 1 | 23 |

23 вычислено из сообщённых −77%. Это стоимость токенов запросов в конкретном сравнении, не общий бюджет проекта, не сравнение GraphRAG с обычным RAG. Полезный контрпример из той же публикации: углубление dynamic search до level 3 повышало среднюю стоимость на 34% на исследованной подвыборке из 29 вопросов. Не смешивать 29 и 50 как один эксперимент.

## 6. Agentic RAG: первичная документация

[LangChain, Retrieval](https://docs.langchain.com/oss/python/deepagents/retrieval).

Two-step RAG выполняет поиск перед генерацией. В Agentic RAG модель решает, когда и как искать; можно подключить разные источники. Время работы становится менее предсказуемым, потому что путь и число вызовов могут меняться. Это архитектурный выбор, а не автоматически следующий уровень качества.

[LangGraph, Build a custom RAG agent](https://docs.langchain.com/oss/python/langgraph/agentic-rag).

Реальный пример: решение искать или ответить → retrieval tool → оценка релевантности → ответ либо переписывание запроса и повтор. Такой цикл удобно показать схемой. Численные обещания «агенты на X% точнее/дешевле» эти страницы не дают. Число попыток, время, расходы и критерий остановки следует ограничивать — это инженерный вывод из повторяющихся вызовов, а не измеренный результат данной документации.

## 7. Экономика: что можно утверждать

Инженерный вывод из механизмов выше: RAG может уменьшать объём контекста относительно пересылки всей коллекции, обновлять документы без переобучения генератора и ускорять доступ сотрудников к знаниям. Экономия труда зависит от реального качества и процесса проверки. Fine-tuning и RAG решают разные задачи и могут применяться вместе.

Общая расчётная модель, не эмпирический результат:

`Total cost = ingestion + indexing + storage + retrieval + reranking + model calls + evaluation + maintenance`.

### Необязательный учебный пример

Все цены вымышленные, только для арифметики. Сравнение выбранных статей расходов при 10,000 запросов, без caching:

- Цена входа: $1 за миллион токенов (условие примера, не тариф).
- Весь документ в каждом запросе: 20,000 входных токенов → $200.
- RAG: 2,000 входных токенов → $20; поиск $0.001/запрос → $10; подготовка индекса $50 → итого $80 по выбранным статьям.
- Разница $120 / 60% относится только к этим допущениям. Output tokens предполагаются одинаковыми, обслуживание и иные расходы не учтены.
- По этим условиям порог окупаемости: $50 / ($0.020 − $0.003) ≈ 2,942 запроса.

Для короткой презентации лучше использовать эмпирический пример Microsoft из раздела 5, а эту арифметику оставить в заметках при необходимости. Полную экономию нельзя выводить из сокращения токенов.

## 8. Скриншоты, которые можно честно получить

- Англоязычная страница исследования Anthropic с графиком/методикой; рядом собственный редактируемый график по её данным.
- Англоязычная страница Microsoft Research с реальной таблицей dynamic selection — подтверждает исследовательскую основу и расходы.
- Диаграмма retrieval agent в официальной документации LangGraph. Подписать как **Official documentation example**, не как собственный эксперимент.
- Собственный программный демо-интерфейс допустим только если реально создан, а результат обозначен как демонстрация, не benchmark.

## 9. Предлагаемый сюжет ровно на 12 слайдов

1. **RAG: Connecting AI to Trusted Knowledge** — тема и исследовательский вопрос.
2. **Contents** — problem / pipeline / improvements / advanced approaches / value.
3. **Why language models need external knowledge** — вступление и актуальность.
4. **How a basic RAG system works** — indexing отдельно от query-time; схема.
5. **Where basic RAG can fail** — missing evidence, lost context, global questions.
6. **Improving retrieval** — hybrid search, context, reranking; график Anthropic.
7. **GraphRAG: Finding connections and themes** — граф и global question.
8. **Agentic RAG: Choosing the next step** — схема с условным повтором.
9. **Which approach fits the task?** — таблица basic / graph / agentic, без выдуманных рейтингов.
10. **How RAG can reduce costs** — механизм затрат и проверенный пример Microsoft 100 →23; скриншот источника при достаточном месте.
11. **Limits and responsible evaluation** — groundedness, retrieval quality, latency, cost, permissions, human review. Метрики/ограничения описывать без обещаний измеренного результата.
12. **Conclusion and selected references** — ответ на исходный вопрос и 3–4 читаемых коротких источника; полные ссылки в speaker notes/DOCX.

Предложение авторское; не является согласованной пользователем структурой. Для B2 сначала раскрыть **retrieval**, **chunk**, **embedding**, **reranking**, **knowledge graph** простыми словами. GraphRAG и Agentic RAG — совместимые направления, а не обязательная линейная лестница улучшений.
